# OMS POS System

A browser-based Point of Sale (POS) system designed for use on computers, tablets and mobile devices.

The system uses a single HTML frontend hosted through GitHub Pages and a Google Apps Script backend connected to Google Sheets.

---

## Features

### POS

- Product and combo selection
- Product categories
- Current order management
- Quantity controls
- Order total calculation
- Order confirmation
- Automatic order number generation
- Order history
- Cashier identification
- Shift statistics

### User Accounts

The POS includes an account-based login system.

Supported roles:

- `admin`
- `cashier`

Each account can have:

- Username
- Password
- Role
- Active/inactive status

Passwords are stored as SHA-256 hashes rather than plain text.

### Admin Panel

Administrators can:

- View registered users
- Create new users
- Change user roles
- Activate users
- Deactivate users
- Reset user passwords
- Manage the POS user system

### Responsive Design

The POS is designed to work on:

- Desktop computers
- Laptops
- Tablets
- Mobile phones

On smaller screens, the three main POS sections are automatically rearranged into a vertical layout.

The browser does not directly modify the Google Sheets spreadsheet.

Instead, the frontend communicates with Google Apps Script, which handles database operations.

## Data Storage

Google Sheets is currently used as the project's database.

The spreadsheet contains several sheets used by the system.

### `Меню`

Contains the products and combos available in the POS.

This data is loaded dynamically when the application starts.

### `История`

Contains completed orders and their information.

The history is shared between all users because it is stored centrally in Google Sheets.

### Users

The user/account data is stored centrally and is used for authentication, permissions and account management.

---

## Order Numbers

Order numbers are generated by the backend rather than relying only on the browser.

This prevents multiple users from accidentally creating the same order number when the POS is being used simultaneously.

The backend reserves the next available order number before the order is saved.

---

## Authentication

When a user logs in:

1. The username and password are entered.
2. The password is hashed using SHA-256.
3. The credentials are sent to the backend.
4. Google Apps Script validates the account.
5. A session is created.
6. The user is granted access according to their role.

The current session is stored in the browser using `sessionStorage`.

Logging out removes the current session from the browser.

## Setup

### 1. Frontend

Upload the project files to a GitHub repository.

The repository should contain the main HTML file used by GitHub Pages.

Enable GitHub Pages from:

    Repository
    → Settings
    → Pages
    → Deploy from a branch
    → main

After deployment, GitHub provides a public Pages URL.

---

### 2. Google Sheets

Create a Google Spreadsheet for the POS data.

Create the required sheets, including:

    Меню
    История
    Users

The exact columns must match the backend implementation.

---

### 3. Google Apps Script

Open:

    Extensions
    → Apps Script

Add the backend code and deploy it as a Web App.

The deployment must allow the frontend to send requests to the Apps Script endpoint.

The resulting Web App URL is then configured inside the POS frontend.

---

### 4. Configure the Frontend

The frontend contains the Apps Script endpoint in the JavaScript configuration.

Example:

    const SHEETS_URL = 'YOUR_APPS_SCRIPT_WEB_APP_URL';

Replace the placeholder with the deployed Apps Script Web App URL.

## Menu Management

Products and combos are not hardcoded into the POS interface.

Instead, they are loaded from the `Меню` Google Sheet.

This means administrators can change the available menu without modifying the frontend code.

After changing the menu data, reload the POS application to retrieve the updated menu.

## Order Workflow

A typical order follows this process:

    User logs in
          ↓
    Menu is loaded
          ↓
    Cashier selects products
          ↓
    Products are added to current order
          ↓
    Total is calculated
          ↓
    Order is confirmed
          ↓
    Backend reserves order number
          ↓
    Order is saved
          ↓
    Order appears in history

Because the order is stored centrally, different devices can access the same order history.

## Security

The system uses several basic security mechanisms:

- Password hashing
- Account roles
- Account activation/deactivation
- Session-based authentication
- Server-side order number generation
- Backend-controlled data operations

However, this project should not be considered a production-grade enterprise authentication system.

Google Sheets and Apps Script are being used as the backend, which introduces limitations compared with a dedicated database and authentication service.

For a larger deployment, a dedicated backend/database would be preferable.

---

## Known Limitations

The current architecture has several limitations.

### Google Sheets as a database

Google Sheets works well for a lightweight POS system, but it is not a traditional relational database.

Very large datasets or high numbers of simultaneous users may require a different backend.

### Apps Script limitations

Google Apps Script has execution and request quotas.

The system is therefore better suited to small and medium-sized deployments than very large commercial POS environments.

### Single-file frontend

The frontend is currently concentrated in a single HTML file.

This makes deployment simple, but as the project grows, separating the application into multiple files would make development and maintenance easier.
